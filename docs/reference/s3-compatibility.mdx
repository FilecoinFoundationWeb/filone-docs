title: S3 Compatibility
description: Which S3 operations work in eu-west-1 and us-east-1, what is not supported, and the workaround for each gap.
---

Fil One provides an S3-compatible API. Standard S3 SDKs and tools work once you set the regional endpoint and enable path-style addressing. Object reads and writes, multipart upload, versioned reads and deletes, Object Lock retention and Legal Hold, and presigned URLs all work in both regions. Authenticate with your [API keys](/security/api-keys).

What doesn't work over the API is listed in [Not supported](#not-supported), each with a workaround where one exists: bucket configuration, ACLs and bucket policies, tagging, lifecycle rules, and event notifications.

## Endpoint

Endpoints are region-specific: `https://s3.<region>.filonecontent.com`, for `eu-west-1` (the default) or `us-east-1`. Use the endpoint for the region your bucket lives in. The full list is in [API Reference: Base endpoint](/reference/overview#base-endpoint).

All requests use HTTPS. HTTP connections are rejected.

## Authentication

Fil One supports **AWS Signature Version 4 (SigV4)** authentication. Any S3 client or SDK that supports SigV4 will work without modification.

| Parameter | Value |
|-----------|-------|
| Endpoint | `https://s3.<region>.filonecontent.com` |
| Region | `eu-west-1` or `us-east-1` |
| Signature version | SigV4 |
| Path style | Required |
| Virtual-hosted style | Not supported |

## Supported operations

:::note About the numeric limits below
Specific size and count limits quoted in these tables (5 TB max object, 5 GB single-PUT, 5 MB / 5 GB part sizes, 10,000 parts, 1,000-object bulk delete) are the **standard AWS S3 values**. Fil One's storage gateway is expected to follow them, but they have not been independently confirmed — see [Limits](/limits).
:::

:::warning How unsupported operations respond in `eu-west-1`
In `eu-west-1`, operations that Fil One does not implement return **`AccessDenied` (HTTP 403)**, not `NotImplemented` (501). This is confirmed in that region.

A 403 from `PutBucketPolicy`, `PutBucketAcl`, `PutBucketLifecycleConfiguration`, or the tagging operations means *the feature is absent*, not that your key lacks a permission. Bucket-configuration calls such as `PutBucketVersioning` and `PutBucketEncryption` can't be granted to any key, so they fail the same way. Don't spend time auditing your access-key scopes for these. Code that branches on `NotImplemented` to degrade gracefully needs to treat 403 on these operations the same way.
:::

### Multipart upload

Multipart upload is supported through the S3 API in **both regions**. Uploads from the Fil One **console** always use a single `PutObject` request, so browser uploads are bounded by the single-PUT ceiling: use the S3 API or CLI for larger objects.

| Operation | Status | Notes |
|-----------|--------|-------|
| `CreateMultipartUpload` | ✅ Supported | |
| `UploadPart` | ✅ Supported | Minimum part size: 5 MB (except last part). Maximum: 5 GB. |
| `CompleteMultipartUpload` | ✅ Supported | Maximum 10,000 parts per upload. |
| `AbortMultipartUpload` | ✅ Supported | |
| `ListParts` | ✅ Supported | |
| `ListMultipartUploads` | ✅ Supported | |

### Versioning

Versioning is **opt-in** and configured at bucket creation time. Once enabled on a bucket, it cannot be suspended or disabled. Every upload to an existing key on a versioned bucket creates a new version rather than overwriting.

The versioning operations are in the tables above: `GetBucketVersioning` and `PutBucketVersioning` under [Bucket operations](#bucket-operations), and `ListObjectVersions`, `GetObject` and `DeleteObject` with `VersionId`, and `CopyObject` with a source version under [Object operations](#object-operations).

The Fil One **console** has no restore, roll-back, or "make current" action — you can list, download, and delete any prior version there, but not promote one to current. In `us-east-1`, you can promote an older version via the API with `CopyObject`. In `eu-west-1`, plain server-side copy works but the version-id form is unverified, so test it against your own bucket first and fall back to downloading the version and uploading it again if it fails.

See [Versioning](/storage/versioning) for detailed usage and examples.

### Object Lock

Object Lock enforces WORM (Write-Once-Read-Many) protection. Both Governance and Compliance mode are supported. Object Lock requires versioning, and both are set at bucket creation time.

Object Lock, retention, and Legal Hold are confirmed in **both** regions. The operations are in the tables above: `GetBucketObjectLockConfiguration` and `PutBucketObjectLockConfiguration` under [Bucket operations](#bucket-operations), and `GetObjectRetention`, `PutObjectRetention`, `GetObjectLegalHold` and `PutObjectLegalHold` under [Object operations](#object-operations).

**Object Lock modes:**

| Mode | Status |
|------|--------|
| Governance | ✅ Supported — the default when you enable Object Lock. No key can be granted the bypass permission, so Governance objects are protected for their retention period in practice. See [Retention modes](/storage/object-lock#retention-modes). |
| Compliance | ✅ Supported — no user, including the organization Owner, can delete a locked object or shorten its retention. |

See [Object Lock](/storage/object-lock) for compliance use cases, retention configuration, and examples.

### Server-side encryption

Encryption is **always enabled** on every Fil One bucket. There is nothing to configure. `GetBucketEncryption` and `PutBucketEncryption` can't be granted to any key, in either region (see [Bucket operations](#bucket-operations)).

| Feature | Status | Notes |
|---------|--------|-------|
| Server-side encryption at rest | ✅ Always on | Applied automatically by the regional storage gateway — no headers required, and it cannot be disabled. |
| Encryption in transit (TLS) | ✅ Always on | All API connections use HTTPS. HTTP is rejected. |
| SSE-S3 (`AES256`) header | Not needed | Encryption is applied automatically in both regions, so send no encryption header. |
| SSE-KMS (`aws:kms`) | ❌ Not supported | Rejected in **both** regions: `InvalidRequest` in `us-east-1`, and `AccessDenied` or `InvalidRequest` in `eu-west-1` depending on the operation. Affects `PutObject`, `CopyObject`, and `CreateMultipartUpload`. Omit encryption headers, server-side encryption is applied automatically. |
| SSE-C (customer-provided keys) | ❌ Not supported | Keys are held by Fil One's storage provider for that region. There is no customer-managed-key option. Requests carrying SSE-C headers are rejected in `eu-west-1`; not yet confirmed in `us-east-1`. Don't send them. |
| Client-side encryption | ✅ Optional | Encrypt data in your own application before upload. AWS's S3 Encryption Client exists only for some SDKs (Java, .NET, Go, Ruby) — not boto3, the CLI, or JS v3 — so with those you supply your own crypto. Server-side encryption is still applied on top. |

See [Encryption](/security/encryption) for details.

## ACLs

The S3 ACL model is **not supported**. Fil One does not implement bucket or object ACLs, bucket policies, or public access controls. All access requires SigV4 authentication.

How an ACL request fails depends on **how** you send it. Confirmed in `eu-west-1`:

| What you send | Behavior |
|---------------|----------|
| A canned-ACL header on an upload (`--acl public-read` in the AWS CLI, `ACL: 'public-read'` on a `PutObject` SDK call) | The flag is silently ignored. The upload **succeeds** and the object is stored, but no ACL is applied and the object does not become public. |
| A dedicated ACL call (`PutBucketAcl`, `PutObjectAcl`, `GetBucketAcl`, `GetObjectAcl`) | Rejected with `AccessDenied` (403). |

So a tool that uploads with `--acl public-read` will appear to work, while a tool that sets ACLs as a separate step will fail outright. In neither case does the object become publicly readable. If you need unauthenticated access to an object, use a [presigned URL](#presigned-urls).

To limit what a key can reach, scope it to specific buckets when you create it. See [Bucket scope](/security/api-keys#bucket-scope).

## Not supported

| Feature | Status | Workaround |
|---------|--------|------------|
| Lifecycle rules (expiration, transitions) | Planned | Run a scheduled script that lists objects with `ListObjectsV2` and deletes old ones with `DeleteObjects`. Objects under Object Lock retention can't be deleted until their retention expires. |
| Event notifications (SNS/SQS/Lambda triggers) | Planned | Poll `ListObjectsV2` on a schedule and compare it with the previous listing. |
| Object and bucket tagging | Planned | Store key-value pairs as user metadata (`x-amz-meta-*` headers) when you upload, and read them back with `HeadObject`. |
| Additional regions | Planned | `eu-west-1` and `us-east-1` are available today. |
| IAM users, roles, and bucket policies on the S3 API | Not supported | Access is controlled by each access key's permissions and [bucket scope](/security/api-keys#bucket-scope): create one key per application with only what it needs. Team members and roles exist in the console: see [Organization](/app/organization#roles-and-permissions). |
| S3 Select | Not planned | Download the object, or a byte range with a `Range` header on `GetObject`, and filter it in your application. |
| S3 Inventory | Not planned | List objects with `ListObjectsV2`, or versions with `ListObjectVersions`. |
| S3 Batch Operations | Not planned | Script the operation over a listing. `DeleteObjects` deletes up to 1,000 objects per request. |
| Multiple storage classes | Not planned | None needed: there is a single storage class. |

## Error responses

Fil One returns standard S3 error XML, in the shape below, for all error conditions.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<Error>
  <Code>NoSuchBucket</Code>
  <Message>The specified bucket does not exist.</Message>
  <BucketName>my-bucket</BucketName>
  <RequestId>abc123</RequestId>
</Error>
```

The **format** is standard, but the specific code returned for a given condition does not always match AWS. If your application only surfaces error messages, no changes are needed. If it *branches* on error codes or HTTP statuses, review the deviations below.

See the [Error Reference](/reference/errors) for a full list of error codes.

### Known error-code deviations in `eu-west-1`

These are confirmed in `eu-west-1`.

| Condition | AWS S3 returns | Fil One `eu-west-1` returns |
|-----------|----------------|------------------------------|
| Any unimplemented operation | `NotImplemented` (501) | `AccessDenied` (403) |
| Reading a bucket or key you cannot see | `NoSuchBucket` / `NoSuchKey` (404) | `AccessDenied` (403) |
| A checksum that does not match the body | `BadDigest` | `InvalidArgument` |
| An unsatisfiable `Range` header | `InvalidRange` | `InvalidArgument` |
| An invalid object tag | `InvalidTag` | `BadRequest` |
| `CreateBucket` on a bucket you already own | `BucketAlreadyExists` in most regions | `BucketAlreadyOwnedByYou` |
| A malformed `PutPublicAccessBlock` or `PutBucketLogging` body | `MalformedXML` for genuinely bad XML only | `MalformedXML` even for a well-formed body, since neither operation is implemented |

Some invalid requests are also **accepted** where AWS rejects them (HTTP 200 or 204 instead of 400). Do not rely on the gateway to validate request parameters for you: validate on the client side where correctness matters.

## Known behavioral issues in `eu-west-1`

These are confirmed deviations that can affect a correctly written S3 client. They are known issues, not intended behavior.

| Area | Issue | Workaround |
|------|-------|------------|
| Pagination | `ListObjects` may return a `NextMarker` with an internal suffix appended to the key (for example `asdf[...]` instead of `asdf`). Feeding that value back as the next `Marker` will not resume where you left off. | Prefer `ListObjectsV2` with `ContinuationToken`, which is unaffected. If you must use `ListObjects`, do not trust `NextMarker`; page using the last returned key instead. |
| URL encoding | With `EncodingType=url`, a space in a key or prefix is encoded as `+` rather than `%20`. Most SDKs decode `%20` only, so keys with spaces can come back wrong. | Avoid spaces in key names, or decode `+` as a space yourself when you request URL encoding. |
| Checksums | Additional-checksum operations are unreliable. `CompleteMultipartUpload` may omit `ChecksumType` from its response, and checksum mismatches surface as `InvalidArgument` rather than `BadDigest`. | Verify integrity with ETags, or compare a hash you compute yourself after download. |

## Differences from AWS S3

Fil One is S3-compatible, not an S3 clone. A few behaviors differ:

| Behavior | AWS S3 | Fil One |
|----------|--------|---------|
| Versioning | Configurable — can be enabled, suspended, or left off per bucket. | Opt-in at bucket creation. Once enabled, cannot be suspended or disabled. No restore/roll-back from the console; achievable via the API in `us-east-1` using `CopyObject`. |
| Server-side copy | `CopyObject` supported. | Confirmed working in `us-east-1`. In `eu-west-1` plain copy works, but the version-id form (promoting an old version) is unverified. |
| Encryption | Optional and configurable. Off by default for older buckets. | Always on. Cannot be disabled. Keys are held by Fil One's storage provider for that region; no customer-managed keys. |
| Bucket management | `CreateBucket` and `DeleteBucket` supported via API. Requires an empty bucket to delete. | Supported via API in `us-east-1`; in `eu-west-1` buckets are managed through the console only. |
| IAM and policies | Full IAM with users, roles, and bucket policies. | No IAM users, roles, or bucket policies on the S3 API. Access is controlled by each access key's permissions and bucket scope. The console has organizations with member roles: see [Organization](/app/organization#roles-and-permissions). |
| Public access | Configurable via ACLs and bucket policies. | No public access. All requests require authentication. Canned-ACL headers on uploads are ignored rather than rejected, and never make an object public. |
| Error codes for missing features | `NotImplemented` (501). | `AccessDenied` (403) in `eu-west-1`. A 403 on a bucket-configuration call means the feature is absent, not that your key lacks permission. |
| Lifecycle rules | Supported (expiration, storage class transitions). | Not supported. Planned for a future release. |
| Object Lock modes | Compliance and Governance. | Compliance and Governance, in both regions, with Legal Hold. |
| Storage classes | Multiple (Standard, IA, Glacier, etc.). | Single storage class. |
| Regions | 30+ globally. | Two: `eu-west-1` and `us-east-1`. Additional regions planned. |
| Data retention after deletion | Object is immediately and permanently deleted. | Object is immediately inaccessible in Fil One. The underlying storage may persist for a bounded period: see [What happens to deleted data](/storage/objects#what-happens-to-deleted-data). |
