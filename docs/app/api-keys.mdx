**API Keys** in the left sidebar is where you create the S3 credentials your tools and code use.

This page covers the console specifically. For what each permission allows, how signing works, and security guidance, see [API Keys](/security/api-keys) and [Authentication](/security/authentication).

## The key list

The page has two tabs, **API keys** and **Connection details**. The table shows:

| Column | What it holds |
|--------|---------------|
| **Name** | The key name, with the Access Key ID underneath and a copy button |
| **Region** | The region the key belongs to, such as `eu-west-1` (hidden on narrow screens) |
| **Buckets** | **All Buckets**, or one badge per bucket the key is scoped to |
| **Permissions** | Badges for the object permissions (**Read**, **Write**, **List**, **Delete**), and a **+***n* badge for the rest. Open the key to see them all |
| **Created by** | The member who created the key, and **Rotated by … on …** once it has been rotated. Shown when your organization has more than one member |
| **Status** | **Active**, or **Expired** from the day after the key's expiry date (UTC) |
| **⋯** | **Rotate** and **Delete**, for the keys you can act on |

With 5 or more keys, a **Search keys** box (by name or Access Key ID) and filters for region (**All regions**) and status (**All statuses**) appear above the table.

Click a key's row to open its details: its **Status**, when it **Expires** (or **Never**), when it was **Created** and **Rotated**, its **Region**, which **Buckets** it reaches ("All buckets in this region" for an unscoped key), and its full **Object permissions** and **Bucket management** permissions. The details panel is the place to check a key's expiry date.

With no keys yet the page reads **No API keys yet** and offers **Create your first key**. A Member sees "You can only see the keys you create. Owners and Admins see every key in the organization." instead, because the organization may hold keys they aren't shown.

If your account is disabled, the **API Keys** page shows only a notice asking you to reactivate your subscription, with no keys, tabs, or **Create new key** button.

:::note Name keys for what uses them
The console doesn't show when a key was last used. Give each key a descriptive name, such as `backup-job-prod`, so you can tell from the list which application would break if you deleted it.
:::

## Who can manage keys

What you can do here depends on your [role](/app/organization#roles-and-permissions):

- **Read only** members cannot create keys. The **API keys** tab explains that keys are managed by members who can create them, and the **Connection details** tab is still available.
- **Members** see, rotate, and delete only the keys they created themselves.
- **Admins** and **Owners** see and manage every key in the organization.

A key can only carry permissions your role holds, and the form hides the ones it doesn't. **Set retention** and **Set legal hold** are Owner-only, so they appear only for Owners. If a member's role is narrowed, any key they created that the new role couldn't create is revoked, and removing a member revokes the keys they created. The member is emailed a list of the revoked keys. See [Organization](/app/organization#removing-a-member).

## Creating a key

Click **Create new key**, which opens a dedicated page.

**Key name.** Up to 64 characters, using letters, numbers, spaces, underscores, hyphens, and periods. Names must be unique within a region, and names starting with `filone-console` (in any capitalization) are reserved.

**Region.** Required, and pre-set to `eu-west-1`. A key is scoped to the region you pick, and each region has its own endpoint, so the endpoint, the region, and the key all need to agree. If you store data in both regions, create a key for each.

**What can this key do?** Object permissions are:

| Permission | Allows |
|------------|--------|
| **Read** | Download and retrieve objects |
| **Write** | Upload and overwrite objects |
| **List** | Browse and list objects |
| **Delete** | Permanently remove objects |

**Read**, **Write**, and **List** are pre-selected. **Delete** is not. For a read-only key, untick **Write**: a key with **Write** can overwrite any object it reaches.

Checking one of those reveals finer-grained permissions nested underneath it. These are granted individually, so tick the ones you need:

- Under **Read**: **Read object versions**, **Read retention settings**, **Read legal hold status**
- Under **Write**: **Set retention**, **Set legal hold**
- Under **List**: **List object versions**
- Under **Delete**: **Delete object versions**

A key with **Write** therefore needs **Set retention** ticked as well before it can apply a retention policy. Unchecking a parent clears whatever was nested under it.

**Bucket management** is a separate section:

- **List all buckets** is always on.
- **Read bucket versioning** and **Read object lock configuration** are available in every region, and both are pre-selected.
- **Create bucket** and **Delete bucket** are available in the regions that support bucket management over the S3 API. In `eu-west-1`, the default region, they are disabled with the tooltip **Not supported in Europe (France)**, and you create buckets in the console instead.

**Which buckets can this key access?** Defaults to **All buckets**, meaning every bucket in the key's region. Choose **Specific buckets** to pick from a list, filtered to the region you selected.

**When should it expire?** **Never expires** (the default), **30 days**, or **Custom** with a date picker. A key with an expiry date works through the whole of that day (UTC) and stops at the start of the next one.

Click **Create API key** to create it.

## Saving the secret

On success a **Save your credentials** dialog shows the **Access Key ID** and the **Secret Access Key**, with the secret masked until you reveal it. You can copy either, or download the pair as a `.csv` or `.env` file.

A downloaded file holds the secret in plain text. Move the values into your password manager, secrets store, or your tool's credential file, then delete the download. Never commit it: if you keep a `.env` in a project, add it to `.gitignore` first.

:::warning The secret is shown once
Fil One never stores your secret, which is why it appears only when a key is created or rotated. Copy or download it before closing the dialog. If you lose it, [rotate the key](#rotating-a-key) to get a new secret.
:::

## Rotating a key

Open the **⋯** menu on the key's row and choose **Rotate**. The **Rotate access key** dialog explains that the key keeps its name, permissions, and buckets, and gets a new Access Key ID and secret. Its region and expiry date carry over too. Confirm with **Rotate key**, and the **Save your credentials** dialog opens with the new pair, shown once as at creation.

The old secret stops working as soon as the new one is issued, so update anything that uses the key. If the old key can't be revoked, a message says the new credentials are ready but the key they replace is still active. Delete the old key from the list yourself in that case.

A few limits apply:

- An expired key can't be rotated, so **Rotate** isn't offered on it. Delete it and create a new key instead.
- **Rotate** only appears on keys your current role could still create. See [Who can manage keys](#who-can-manage-keys).

After a rotation, the **Created by** column shows who rotated the key and when.

## Revoking a key

:::warning Deleting a key breaks anything that uses it
A deleted key stops working immediately and can't be restored. To move an application onto a key with different permissions or buckets, create the new key first, switch the application over, then delete the old one.
:::

Open the **⋯** menu on the key's row and choose **Delete**. The dialog warns that the key will be permanently revoked and that any application using it loses access immediately. Deleting a key is how you revoke it.

To delete several keys at once, tick their checkboxes (or the header checkbox). A bar shows *n* **selected** with **Clear** and **Delete**. Only keys you're allowed to delete can be selected.

A key stays in your list until its revocation is confirmed, so a key that is still listed is a key that still works.

:::note Keys for a bucket
A bucket's **API Keys** tab shows the keys that can reach that bucket, which is a quicker way to audit access for one bucket than reading down the full list.
:::
